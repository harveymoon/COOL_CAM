# Cool CAM — notes for Claude

- Monorepo with npm workspaces. Library packages (`core`, `post`, `sim`, `mcp`) compile with `tsc -b` to `dist/`; the viewer aliases them to `src/` so it needs no build.
- `npm test` runs vitest across `packages/*/test`. Keep tests passing; add one when you add an operation or importer feature.
- The MCP server (`packages/mcp`) must be rebuilt (`npm run build`) before Claude Code picks up changes; it is launched from `.mcp.json`.
- Coordinate/orientation conventions live in `packages/core/src/ops/profile.ts` and `pocket.ts` (Clipper returns outers CCW / holes CW; climb = material on the right).
- Safety-relevant code: `packages/post` (tool change + G53 moves) and `packages/sim` (rapid-into-stock, below-stock). Be conservative when changing them.
- Style: dark theme, no rounded corners anywhere in the viewer.
- The local API (jobs, tool library, fonts, `/api/events` SSE change feed) is `packages/server` (`createApi` handler + `startServer` with the built viewer). Vite mounts it as middleware (`coolCamApi` in `packages/viewer/vite.config.ts`), `packages/desktop` (Electron, electron-vite, ESM main) hosts it in production, and `npm start` / `cool-cam` serves it to a browser. Project model: nothing loads on boot; `Landing.tsx` lists the jobs folder (`GET /api/jobs` returns per-project summaries and whether a `<slug>.jpg` thumbnail exists) and the user opens or creates a named project explicitly. The open project autosaves to `<slug>.json` via `PUT /api/jobs/<file>`; the server mirrors every save to `jobs/current.json`, which is only the "job being worked on" pointer the MCP server follows (it re-reads it when its mtime is newer than its own last write). If the MCP server switches jobs, the viewer shows a notice (`mcpSwitched`) instead of following. Thumbnails: `scene.snapshot()` 1.5 s after each simulation result, `PUT /api/jobs/<slug>.jpg`; `DELETE /api/jobs/<slug>.json` removes json, jpg and nc. Toolpaths are generated in `gen.worker.ts` (cancel = terminate + restart). Desktop: `npm run dev:desktop` (HMR in a window), `npx electron packages/desktop [--screenshot out.png]` for the production path, `npm run build:desktop` to package, then `npm run install:desktop` to copy it to `~/Applications` and run it from there (never run the copy in `dist/`: rebuilding under a running app crashes it). Packaged-app log: `~/Library/Logs/Cool CAM/main.log` (see `docs/PACKAGING.md`).
- Viewer structure: `ui.tsx` (context with job store, selection, sim, modals), `scene.ts` (all three.js, view cube, cameras), `actions.ts` (menu/panel actions), `panels/*` (dockview panels), `modals/*`, `layout.ts` (dockview layouts in localStorage). Dockview 8 via `dockview-react`.
- Tool library: the user's own library lives in their app-data folder (`packages/core/src/node-paths.ts`: macOS `~/Library/Application Support/Cool CAM/tools.json`, Windows `%APPDATA%\Cool CAM`, Linux `~/.config/cool-cam`; `COOL_CAM_DATA_DIR` / `COOL_CAM_LIBRARY` override). `library/tools.json` in the repo is the read-only bundled default that seeds the user library on first use. Both the Vite plugin (`/api/tools`, `/api/tools/info`, `/api/tools/defaults`) and the MCP server (`library_tools`) resolve it through `resolveToolLibrary`, exported as `@cool-cam/core/node` (never import that from browser code). The library modal has a grid view of rendered 3D cutters: `toolGeometry.ts` builds the mesh (shank, helical flutes, flat/ball/V/drill/keyhole tip, colour from the coating in the name or `color`) and is shared by the thumbnails (`toolThumbs.ts`, one offscreen renderer with a cache, because browsers cap WebGL contexts), the live preview (`ToolPreview3D.tsx`) and the cutter shown moving in the viewport (`scene.ts` keeps one model per tool id). `ToolGlyph.tsx` is the SVG fallback without WebGL; a tool's `image` field overrides both.
- 3D pipeline: `packages/core/src/mesh.ts` (heightmap rasteriser, drop-cutter offset surface, marching squares), `ops/surface.ts` (cached per model/tool/res), `ops/rough3d.ts` + `ops/finish3d.ts`. Safety margins: offset radius is enlarged by 0.71×res and roughing regions shrink by 0.5×res so interpolation between samples never lands inside a wall. `test/mesh.test.ts` has a gouge check against a fine heightmap; keep it passing.
- `geometry/polyline.ts#simplify` is Douglas–Peucker; the old local-collinearity version collapsed smooth loops.
- Feature extraction: `packages/core/src/features.ts` (`extractFeatures` groups upward-facing triangles by Z into planar levels via Clipper unions; `footprintAbove(z)` projects the mesh above a plane; `proposeOperations` builds level pockets from `domain − footprintAbove(z)`, rest passes, drills, 3D ops and a cutout). Test STL for it: `examples/stl/bracket-2p5d-12mm.stl`.
- 3D machining boundary: `ops/boundary.ts` (`boundaryFor` → boundary + tool-centre `allowed` polygons; `maskFromPolygons` rasterises it). `surface.ts` sizes the heightmap from `allowed` and exposes `offMasked` (used by finish3d); rough3d clips exact contours with `allowed` instead, for smooth rings. Defaults: silhouette, containment inside, offset 0; `proposeOperations` and the example jobs use containment outside + offset for a moat.
- New ops: `ops/vcarve.ts` (offset-based V-carve; depth is always clamped at the V flank and the stock; advanced flat clearing is returned via the `flatMoves` map and emitted by `generateToolpaths` as a separate toolpath with id `<opId>:flat`), `ops/keyhole.ts`. `ops/profile.ts` has ramp entry via `walkLoop`; `ops/pocket.ts` has `restToolId`.
- Profile loops are prepared once by `prepareProfileLoops` (orientation, ordering, seam moved out of any tab); `generateProfile` and the viewer's tab markers (`profileTabCenters`) both use it so markers match the cut. Each pass continues from the arc length where the previous ramp ended (`rotateLoopAt`); a plunge never lands inside a tab.
- Post: G2/G3 are only fitted over constant-Z runs and carry a Z word if the Z ever differs; the first traverse after a tool change is at the job's safe Z. `packages/post/test/roundtrip.test.ts` replays emitted G-code against the toolpath; keep it passing when touching the post.
- MCP `JobState.save()` never re-reads `current.json` (only `require()` does), so `new_job`/`load_job` cannot be clobbered by a newer viewer save.
- Safety net: every `Toolpath` carries `stepdown` (planned max axial engagement); the simulator measures, per cutting move, the tallest column of material above the cutter's surface (inner footprint cells only) and how far into the cutter it reaches. Bulk material deeper than the plan → `deep-engagement` error; deeper than the flute length → `shank-contact` error; plunges > 2 diameters → warning. MCP `export_gcode` refuses while the simulation has errors (`force` overrides); the viewer asks before downloading. Keep `packages/sim/test/engagement.test.ts` and `packages/core/test/planner-fuzz.test.ts` passing; run `PLANNER_FUZZ=300 npm test` for a deeper search after planner changes.
- `contoursBelow` assembles marching-squares loops by exact grid-edge keys (never coordinate tolerance); a loop that fails to close throws rather than dropping a hole. `rough3d` additionally rasterises each level's region and refuses a level that covers model samples. `ringsFor` adds fill rings where a stepover wider than the tool radius would leave a strip in a neck of the region.
- Text: `core/src/text.ts` (opentype.js via an interop shim, because its CommonJS build exposes `parse` differently under Node ESM and Vite; fonts are loaded by the caller: Vite `/api/fonts` in the viewer, system font dirs in the MCP server). Images: `core/src/image.ts` (`heightmapToMesh`, Node `decodeImage`). Arcs: `post/src/arcs.ts` (`fitArcs`).
- Viewer: shapes carry `params` (rect/circle/regular_polygon/slot/text) so the Parameters panel (`ShapeParams.tsx`) can edit them; pure translations keep params, other transforms drop them. Undo lives in `store.ts` (60 steps).
